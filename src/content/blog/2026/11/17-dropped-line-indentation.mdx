The problem is: how to do a _dropped line_ in CSS? What is it? Let me quote from [Wikipedia](https://en.wikipedia.org/wiki/Dropped_line):

## The Faux “Dropped Line” Technique

To repeat the above example, alongside the corresponding HTML and CSS code:

<style>{`
.drop-lined p,
p.dropped-line {
	font-size: var(--FONT-SIZE--SMALL);
	margin: 0;
}
`}</style>

<LiveExample>
```html
<div class="drop-lined">
	<p><span>It’s linkage I’m talking about,</span> <span>and harmonies and structures,</span></p>

	<p>And all the various things that lock our wrists to the past.</p>

	<p><span>Something infinite behind everything appears,</span> <span>and then disappears.</span></p>
</div>
```
```css
.drop-lined span {
	vertical-align: top;

	&:not(:first-of-type)::before {
		content: "\A\2060";
		white-space: pre;
		display: inline-block;
	}
}
```
</LiveExample>

### How Does It “Work”?

The important parts:

1. Each part of the paragraph, on both sides of the “break”, needs to be wrapped in an inline element, in our case — `<span>`.

2. This inline element needs to have `vertical-align: top`.

3. For each non-first span, we add an inline-block `::before` pseudo-element with some very specific `content` and `white-space: pre`.

4. That `content` consists of an escaped newline symbol followed by an escaped [“word joiner”](https://en.wikipedia.org/wiki/Word_joiner) symbol.

This is how this works. But _why_? Let me quote [the spec](https://drafts.csswg.org/css-inline/#valdef-baseline-shift-top) for the `top` value of `vertical-align`:

> Align the [line-over](https://drafts.csswg.org/css-writing-modes-4/#line-over) edge of the [aligned subtree](https://drafts.csswg.org/css-inline/#aligned-subtree) with the line-over edge of the [line box](https://drafts.csswg.org/css-inline/#line-box).

Ok, maybe this is not very clear… I don’t know if there is a good explanation of how exactly read this…

---

And that’s where I stopped writing this post when I last tried to finish it, as by trying to understand and explain what exactly was happening, I realised _it does not work_.

### Why This Is Not It?

While the above example _did_ work, to see where it won’t work let’s look at this example — three lines from Audre Lorde’s poem “Memorial III — From a Phone Booth On Broadway”

```html

		that works<br/>

		<span>I must call you</span><br/>
		now
	</p>
</div>
```

The technique in the above example worked, but _only once_ — there is a drop after the first “quick”, but not after the second.

When the sentences were long, that semi-working technique worked because there was only one drop per line box. And the way technique worked is that it aligned the first part at the _top_, then inserted a dropped line, and this whole “block” that included the line drop was still aligned to the top — but not relative to the _preceding text_, but to the whole line box.

And because in each of the two spans with the inserted pseudo on one line the _newline_ was inserted only once, that’s how far from the top of the line box they were aligned.

---

Oh well! A good part about this technique — it has good browser support, and for longer lines it can be used pretty effectively.

## Proper “Dropped Line” Technique

After putting the draft of this post back into the drawer, and finishing a [replacement post](/explicit-nesting/) I published on that day, I went to sleep.

And, of course, in bed, I came up with a way to solve this _properly_. Well, “properly” — the technique is a bit hacky and requires very modern CSS features — `sibling-index()` and `sibling-count()`.

Look:


<LiveExample class="require-sibling-count" shouldHideHTML caption="Now that works, indeed. Not 100% as in print — I did not remove the horizontal spaces, but that is not a part of the technique, and is not that interesting.">
```html
<div>
	<p class="dropped-line">
		that works
		<span><br/>quick</span>
		<span>quick</span>
		<span>I must call you</span>
		now
	</p>
</div>
```
```CSS
.dropped-line {
	display: block;

	& > span {
		position: relative;
		top: calc((sibling-index() - 1) * 1lh);

		&:last-child::after {
			content: "";
			display: block;
			height: calc((sibling-count() - 1) * 1lh);
		}
	}
}
```
</LiveExample>

And this still works with the longer sentences, here is our first example, but using the new technique:

<LiveExample class="require-sibling-count" shouldHideHTML>
```html
<div>
	<p class="dropped-line"><span>It's linkage I'm talking about,</span> <span>and harmonies and structures,</span></p>

	<p class="dropped-line">And all the various things that lock our wrists to the past.</p>

	<p class="dropped-line"><span>Something infinite behind everything appears,</span> <span>and then disappears.</span></p>
</div>
```
</LiveExample>

### And How This Works?

Well, it is pretty simple, and is in line with both how Richard was trying to do it, and how I experimented with it a long time ago — using `position: relative`, but where previously we did not have a `lh` unit, as well as `sibling-index()` and `sibling-count()` functions, now we can use those to achieve what we need:

1. [`lh` unit](https://www.w3.org/TR/css-values-4/#lh) is great to get the value of our line-height (although, we need to note that this is only a _metric_, and not the actual rendered height of the line box, as it can be modified by various things — I recommend [“Deep dive CSS: font metrics, line-height and vertical-align”](https://iamvdo.me/en/blog/css-font-metrics-line-height-and-vertical-align) article by [Vincent De Oliveira](https://iamvdo.me/) about this).

2. [`sibling-index()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/sibling-index) allows us to incrementally shift each consequtive fragment as a whole — be it a single word or a sentence, we just need to wrap each full fragment with a span.

3. Because we’re using `position: relative`, our layout _around_ the shifted lines does not know that it needs to adjust to this. But what we can do is insert a pseudo-element after our last inline fragment, make it block, and give it the height equal to the accumulated shift, which we can know due to [`sibling-count()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/sibling-count) and how it evaluates on pseudo-elements — it uses the value from the originating element. And a block element “drops” from the inline one, giving the vertical space between our fragment and anything that follows it.

### Browser Support and Fallbacks

Above examples work only in browsers that support `sibling-index()` and `sibling-count()` — and those are “baseline available” since August 2026 — but, of course, older browsers won’t get anything. It won’t break, and the text will just go in one line.

I did not add any workarounds for that in this post, but if you really want those, I wrote an article about this: [“Possible Future CSS: Tree-Counting Functions and Random Values”](https://kizu.dev/tree-counting-and-random/) in 2024.


## That’s It!

I think that CSS for typesetting poetry can be really interesting. When you look at the old books, or how people used typewriters to format stuff, not everything can be moved to CSS in any straightforward way.

When I was doing research for the examples in this article, I stumbled upon so many places where in modern editions or reprints of various poetry that relied on indentation, the final indentation did not look good, was fully absent, or looked not as intended. I wish more people explored how to reproduce those previously print-only techniques on the web, so we could preserve the original visual intent.
